Core Definitions

  • Identity Administration – managing identity objects across their lifecycle.
  • Centralized Identity Management – single tool storing/managing credentials for AuthN/AuthZ (on-prem or cloud), run by an identity authority.
  • Decentralized Identity – people/orgs/things interact transparently and securely via an identity trust fabric.
  • Identity – an object that can be authenticated. Account – an identity with associated data.
  • Microsoft Entra Account – identity created via Entra ID or another MS cloud service (e.g., M365).
  • Tenant – a dedicated, trusted instance of Entra ID, auto-created when an org signs up for a MS cloud subscription.
  • Administrative Unit – a partitioned piece of a tenant used to create an admin boundary.
  • PHS (Password Hash Synchronization) – simplest way to enable on-prem auth in Entra ID; no extra infrastructure needed.
  • Connector Space (CS) – staging area per connected directory before the provisioning engine processes objects (Entra ID has its own CS; so does each forest).
  • Metaverse (MV) – single central store where synced objects are created per sync rules.
  • Sync Rules – determine which objects get created/connected in the MV.
  • Run Profiles – bundle the steps for copying objects/attributes between staging areas and connected directories.

Identity Landscape & Zero Trust

Five-layer model: Zero Trust → Identity → Actions → Usage → Maintain.

  • Zero Trust principles: Verify Explicitly, Use Least Privilege, Assume Breach.
  • Identity sources: B2B, B2C, Verifiable Credentials, Decentralized Providers.
  • Actions: Authenticate (AuthN), Authorize (AuthZ), Administer, Audit.

Verify Explicitly – validate: user ID/location, device health, service/workload context, data classification, anomalies.
Least Privilege – enforced via: Just-in-Time (JIT), Just-Enough-Access (JEA), risk-based adaptive policies, data protection against out-of-band vectors.
Assume Breach – segment access by network/user/device/app; encrypt sessions end-to-end; use analytics for detection/posture/defense.

Identity as a Control Plane – directs access to resources based on specific criteria (analogous to a network control plane).

What identity gives you:

  • Authentication (prove who/what you are) – user sign-on experience, trusted sources, federation protocols, level of assurance.
  • Authorization (get permission to do something) – can a user access this resource, and what can they do once they do.
  • Administration (IT-managed and self-service) – single-view management, application of business rules, automated requests/approvals/access assignment, entitlement management.
  • Auditing (report on what was done) – track who does what, when, where and how; focused alerting; in-depth collated reporting; governance and compliance.

Usage layer: access applications and data, secure them (cryptography), and manage licences. Maintain layer: keep systems up to date – Protect, Detect, Respond.

Authentication, Authorization, Tokens & Claims

IdP components: repository of identities, authentication system, security protocols, a trusted party.
Protocols: OpenID Connect (OIDC) – built on OAuth2, standardized message flows for identity. SAML – open standard for exchanging AuthN/AuthZ data between IdP and service provider.

Security Tokens:

  • Access Token – issued by auth server in OAuth2 flow; carries user + resource info; used to access APIs.
  • Refresh Token – issued alongside access token since access tokens are short-lived.
  • ID Token – sent to client as part of OIDC flow.
  • JWT – open standard (RFC 7519) for compact, self-contained JSON-based transmission of claims.

Claims concepts: Claim (a data value pair in a token), Assertion (a package/token sharing identity/security info across domains), Attribute (a value pair within a token), Augmentation (adding extra claims to a user token for more detail).

Common types of Authorization:

  • Access Control Lists (ACLs) – explicit allow/deny list for entities.
  • Role-Based Access Control (RBAC) – most common authorization approach.
  • Attribute-Based Access Control (ABAC) – rules applied to entity/resource/environment attributes.
  • Policy-Based Access Control – combines business role with policy to determine access.

Licensing

  • Entra ID P1/P2 – unlocks premium features. P2 required for PIM; any user who assigns/manages PIM assignments needs a license, but a user simply holding a privileged role does not.
  • M365/Office 365/Windows licenses – one per user needing access to those products.
  • Monthly Active User (MAU) license – used with Entra External Identities; billed via a monthly report of external users who logged in.

Lifecycle Management

Foundation of Identity Governance. Typical process:

  • Identify existing authoritative systems of record (e.g., HR system).
  • Compare the system of record against directories/databases used by apps; resolve inconsistencies.
  • Determine processes to supply authoritative info for visitors.

Monitoring services: Azure Monitor, Application Insights, Service Health, Resource Health, Resource Manager, Azure Policy.

Entra ID Roles & Tenant Configuration

  • Member users can: register applications, manage their own profile photo/mobile number, change their own password, invite B2B guests.
  • Guest users have restricted permissions: manage own profile, retrieve limited info on other users/groups/apps, cannot read all directory info.

External Collaboration (B2B)

  • Collaboration – external users sign in with their preferred identity; represented as guest users in your directory.
  • Direct Connect – mutual two-way trust with another Entra org for seamless collaboration (currently supports Teams shared channels).

Invitation Redemption Flow:

  • User-based discovery checks whether the user already exists in the tenant (if UPN matches both an existing account and a personal MSA, user is prompted to choose).
  • If SAML/WS-Fed federation is enabled, Entra ID checks the domain suffix and redirects to the pre-configured IdP.
  • If Google federation is enabled, checks for gmail.com/googlemail.com suffix and redirects to Google.
  • If the user has an existing personal MSA, they sign in with it.
  • Once home directory is identified, user is sent to the corresponding IdP.
  • If no home directory is found and One-Time Passcode (OTP) is enabled, a passcode is emailed; if OTP is disabled, the user is prompted to create a consumer MSA.
  • After IdP authentication, user is redirected to Entra ID to complete consent.

External Identities – Primary Scenario: collaboration via MS or custom apps; supports any work/school/any email address as IdP; users managed in same directory as employees but annotated as guests; SSO to all Entra ID supported; security/compliance managed by the host org; host branding used.

UserType: Member – employee/payroll user of the host org. Guest – not considered internal to the company.

Microsoft Entra Verified ID – decentralized identity solution to issue/verify credentials. Requirements: Azure tenant + subscription, Entra ID Premium license, Global Administrator account, Azure Key Vault instance.

Configuring External IdPs / Federation

  • SAML/WS-Fed IdP federation (formerly “Direct Federation”) works with any IdP supporting SAML 2.0.
  • Setting up federation does not retroactively change the auth method for guests who already redeemed invitations — they keep using whatever method they redeemed with, even if federation is later added, changed, or the partner org migrates to Entra ID.
  • Deleting federation with a partner’s IdP locks out guests currently using it.
  • The target domain for direct federation must not be DNS-verified on Entra ID.

Hybrid Identity (Entra Connect)

Microsoft Entra Connect bridges on-prem AD with cloud Entra ID:

  • Synchronization – creates users/groups/objects; matches identity info (incl. password hashes) to cloud.
  • Password Hash Synchronization – syncs hash of on-prem AD password.
  • Pass-through Authentication (PTA) – same password on-prem and cloud, without federation infrastructure.
  • Federation integration – optional, uses on-prem AD FS for hybrid.
  • Health Monitoring – via Entra Connect Health.

Authentication method comparison:

  • PHS: least effort/infra; runs sync every 2 minutes; pair with seamless SSO to reduce prompts; supports leaked-credential reporting via Identity Protection; highly available cloud service; does not immediately enforce on-prem account state changes; good for HA/DR, on-prem outage survival, Identity Protection.
  • PTA: requires one+ lightweight agents on existing servers with access to on-prem AD DS (incl. DCs); supports seamless SSO; enforces on-prem account policy at sign-in time; recommend 2 extra PTA agents for HA; PHS can serve as backup auth if agents can’t validate credentials during major on-prem failure.
  • Federated Authentication: relies on external trusted system; needed for smartcard/cert auth, on-prem/third-party MFA requiring a federated IdP, third-party auth solutions, or sign-in requiring sAMAccountName (DOMAIN\username) rather than UPN; needs load-balanced server array; requires significant on-prem investment.

sourceAnchor attribute – immutable identifier linking on-prem and cloud objects:

  • Links new/rebuilt sync engine server objects to on-prem objects.
  • Enables “hard match” when moving from cloud-only to synced.
  • Combined with UPN to uniquely identify a user in federation claims.
  • Rules: <60 characters, no special characters, globally unique, string/integer/binary type, not based on user’s name, not case-sensitive, assigned at object creation.
  • For a single on-prem forest, use objectGuid (alternative: employeeID).

Microsoft Entra MFA

Risk-mitigation features alongside MFA: password complexity/expiration rules, SSPR, Identity Protection (risk-based policies), Password Protection (banned-password list), Smart Lockout, Application Proxy, SSO, Entra Connect.

MFA factors: something you know (password/security question), something you possess (mobile app/token device), something you are (biometric).

MFA requires one of: Entra ID P1/P2, M365 Business, Entra ID Free, or M365 standalone.

Azure Resources / Managed Identities

Managed Identity benefits: no need to manage credentials; can authenticate to any resource supporting Entra authentication.

User Authentication Methods

FIDO2 Security Keys – typically USB, also Bluetooth/NFC; unphishable, specification-based, passwordless; open FIDO specification lets users sign in without username/password.

Windows Hello for Business (WHFB) – addresses password weaknesses (hard to remember/reused, server breach exposure, replay attacks, phishing).

  • Based on certificate or asymmetric key pair; credentials/token can be bound to the device.
  • IdP validates user ID and maps the Hello public key to the account.
  • Keys generated in TPM 1.2/2.0 for enterprise, 2.0 for consumer/software.
  • 2FA = key/cert tied to device; private key never leaves the device when using TPM.
  • PIN entry or biometric gesture triggers Windows to cryptographically sign data sent to the IdP.

Smart Lockout – locks account from sign-in for 1 minute after 10 failed attempts; re-locks after each subsequent failed attempt; always on for all Entra ID customers.

Conditional Access

Security Defaults – MS-managed baseline settings until an org is ready to manage its own: require MFA registration for all users, require MFA for admins, block legacy auth protocols, require MFA when necessary, protect privileged activities (e.g., Azure portal access).

CA Policy Benefits: increased productivity, risk management, compliance/governance, cost management, Zero Trust alignment.

Access Tokens (in CA context) – enable clients to securely call protected APIs for AuthN/AuthZ.

Common CA Policies: require MFA, respond to potentially compromised accounts, require managed devices, require approved client apps, block access.

Identity Protection & Risk Policies

Identity Protection lets orgs view account security posture via three tasks: automate detection/remediation of identity-based threats, investigate risks via portal data, export risk detection data to third-party tools.

Risk policy types:

  • Sign-in risk policy – analyzes the sign-in activity itself; probability the sign-in wasn’t performed by the legitimate user.
  • User risk policy – detects probability that a user account is compromised, based on atypical behavior patterns.

Microsoft Defender for Identity

Cloud-based security solution using on-prem AD signals to identify, detect, and investigate advanced threats, compromised identities, and malicious insider activity:

  • Monitors users/entities/activities with learning-based analytics.
  • Protects identities/credentials stored in AD.
  • Identifies/investigates suspicious activity and attacks across the kill chain.
  • Provides clear incident timelines for fast triage.

Components:

  • Defender portal – central management/investigation of threats.
  • Defender for Identity sensor – installed directly on Domain Controllers and AD FS.
  • Defender for Identity cloud service – runs on Azure infrastructure.
